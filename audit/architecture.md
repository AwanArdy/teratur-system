# Architecture and audit scope

TERATUR-ID backend is a multi-tenant Indonesian F&B operations API. Node/TypeScript Express 5 and Drizzle/postgres-js handle identities, organizations, outlets, catalogs, inventory, POS/sales, expenses, workforce/payroll, reports and optional AI advisor forwarding. Both /api/v1 and /api mount the same router (src/app.ts:67-94).

Principals are anonymous callers, organization owner/admin/staff, optional linked staff records, backend DB service, and an optional external RAG service. Protected resources include identity/session capabilities, other organizations' data, outlet operations, employment/payroll information, financial/inventory integrity and paid service entitlements. Authentication reloads live sessions, users and memberships (src/middleware/authenticate.ts:9-82). Organization roles and plans have separate middleware. Outlet context currently loads all organization outlets; PRD outlet assignment policy needs careful comparison rather than assumed correctness.

Public identity flows include onboarding/OTP, login, refresh, reset and logout. Entry inputs include JSON, path/query selectors, Bearer and outlet/idempotency headers. Sensitive flows include foreign-object references into catalog/staff/warehouse resources; concurrent sale/cancel, transfer/receipt, stock approval and shift close; report/AI copies and exports; subscription selection; and credential logging. Role policy must be established from source requirements, not assumed from missing middleware.

Source deployment is a PostgreSQL-only Compose service plus documented build/start. Runtime configuration controls signing material, DB, CORS and optional RAG forwarding. Production ingress/TLS, DB policies, billing integration, log readership and downstream RAG policies are unobserved. Do not probe any deployed service. No meaningful comparable baseline was established.

Read-only reconnaissance covered all modules, schemas, tests and manifests. npm run build and npm test require existing dependencies; tests mock important boundaries and do not prove actual DB isolation. No target-controlled execution is approved: OS primitives exist, but combined scratch-only writes and aggregate process-tree CPU/memory/PID/disk limits are not established. Do not run builds, tests, harnesses, application imports or target validators outside the required sandbox. Source-grounded candidates therefore remain needs_validation unless independently bounded execution becomes possible. Do not install dependencies or read credential files.
